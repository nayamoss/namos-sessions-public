# Public embeds — responsive iframe height — Requirements

**Type:** Improvement
**Status:** In Review
**Priority:** High
**Last Updated:** 2026-08-22

## Problem Statement
Every public embed (`/embed/:id` — Agenda, Schedule itinerary, Schedule grid, Session list,
Speaker gallery, Speaker list) is served for iframe embedding via a snippet generated by
`iframeSnippet()` in `src/lib/public-embed.ts`. That snippet sets `width="100%"` (genuinely
responsive) but a **hardcoded pixel `height`** per view — 760/720/880/900 — chosen once at
copy-time and never revisited.

The embed's own content already reflows correctly by width (Tailwind `sm:`/`lg:` breakpoints
throughout `EmbedRenderer.tsx` and `EmbedPage.tsx` stack correctly on narrow viewports). The
actual defect is **height**: content height varies enormously with event size, track count, and
viewport width (narrower iframe → same content wraps to more rows → taller), but the iframe
height a host page renders never adapts. Result: on any event bigger or smaller than whatever
the constant assumed, or on any narrow/mobile embed, content either gets clipped with an
internal scrollbar or leaves dead whitespace. Confirmed as an open, untested risk in
issue #257 ("iframe height collapse" is explicitly called out as untestable by component tests).

## Functional Requirements
- FR-001: The embed page (`PublicEmbedPage.tsx`) observes its own rendered content height and
  reports height changes to its parent window via `postMessage`, scoped to its own `embedId` so
  multiple embeds on one host page never cross-resize each other.
- FR-002: The generated `<iframe>` snippet (`iframeSnippet()`) includes a small inline listener
  script (no external dependency, no npm package) that receives that message, validates the
  origin against the embed's own `src` origin, and sets the iframe's height to match — with no
  internal scrollbar once synced.
- FR-003: If the host page's CSP blocks inline scripts, or postMessage never arrives (JS
  disabled, sandboxed iframe without `allow-scripts`), the iframe keeps working exactly as
  today — falls back to the existing static `iframeHeight(view)` default. No regression for
  hosts that can't run the resize script.
- FR-004: Height updates are debounced so tab switches, filter changes, and detail-panel
  open/close (all of which change content height today) resize smoothly without layout thrash
  or postMessage spam.
- FR-005: Works correctly with more than one embed on the same host page at once (e.g. an
  Agenda and a Speaker gallery on the same CMS page) — verified by `embedId`, not by view type
  or iframe index.
- FR-006: The admin-side live preview (`EmbedPreviewPanel.tsx`) reflects the same resize
  behavior so what an organizer sees while editing matches what actually ships.

## Non-Functional Requirements
- NFR-001: No new runtime dependency — implemented with the platform `ResizeObserver` +
  `postMessage` APIs already available in every supported browser, matching this project's
  existing "no external CDN/script" posture for the embed snippet.
- NFR-002: postMessage payload carries no PII beyond what the embed already renders publicly;
  only `{ source, embedId, height }`.
- NFR-003: No perceptible flash/jump on initial load — first paint should already report a
  reasonably close height so the fallback-to-observed transition isn't visually jarring.

## Out of Scope
- Rewriting `EmbedRenderer`/`EmbedPage` layout or breakpoints — the width-based responsive
  behavior already works and is not touched.
- A user-facing "auto height on/off" toggle in the embed editor — always-on is the correct
  default; revisit only if a real host surfaces a reason to opt out.
- Fixing the underlying reactive-subscription/socket-drop defect tracked separately in
  issues #211/#217 — unrelated failure mode, referenced in #257 but not this issue.
- Browser/device-width click-through verification of all nine competition-brief requirements —
  that is issue #257's scope; this issue's fix is one of the things #257 will verify.

## Success Metrics
- Copying the generated iframe snippet into a third-party page and resizing the browser window
  (or the iframe's container) never produces an internal scrollbar or excess whitespace, at
  320px, 390px, 768px, and 1280px+ container widths.
- Switching day tabs / opening a session or speaker detail panel inside the embed resizes the
  host iframe smoothly, no clipped content.
- Two different embeds pasted on the same host page resize independently and correctly.
- A host page with `sandbox="allow-scripts"` omitted (or postMessage otherwise unavailable)
  still renders a usable, non-broken embed at the existing static height.
